- **Ask, Don't Guess**: When goals, scopes, or implementation choices have ambiguity, ask the user explicitly with selectable options instead of silently assuming. Worked reliably five times in one session (2026-10-04) — keep using concrete option lists. A long, prescriptive task brief does **not** remove this need: such briefs are often written for an external runner AI, and the shapes they specify may not match the user's mental model of his own project. Confirm the design forks anyway, even when the brief answers them. Link [[project-model-config-decisions]].
- **Intent Alignment Before Action (Never Probe or Edit When User Asks "懂我意思吗")**: When the user asks "懂我意思吗？" or discusses exploratory design thoughts/feelings ("太长了", "这设计好不好"), do NOT immediately fire terminal probing commands or start editing. Answer their question directly in plain language first, clearly articulate your exact understanding of their intent and your honest design view, and wait for confirmation. The same stop applies when he **retracts his own answer** — answering a multiple-choice question and then adding "我那个回答问题回答的可能有点问题，你先跟我核对一下意思" means the question's framing was wrong, not that he changed his mind. Do not treat the selected option as settled and start work; restate the intent in his words, say what you would build, and wait.
- **Plain Language & Vibe Coding (Zero Translated Jargon)**: Explain outcomes, mechanisms, and options in everyday Chinese using concrete before/after text examples and physical metaphors (e.g., "记账本里的门牌号/第几个字", "给带黑块的句子上锁"). Never use raw or translated technical jargon like "内联锚点" (inline anchor), "字符偏移量" (character offset), or AST/schema terminology—the user explicitly states "我完全不懂编程，说人话".
- **Surgical Precision**: Minimal diff scope. Never perform unsolicited refactoring or wipe unrelated logic.
- **Restrained Verification**: For small, targeted edits, analyze logic and verify directly affected scope only; do not run exhaustive end-to-end suites unless necessary. Baseline is assumed working.
- **Hand Off Human-Easy Checks**: Visual inspections, browser interaction, clicking, and eye-checks should be handed off to the user with clear instructions rather than struggling in loops.
- **Dual-Directional Learning**: Anchor both user corrections (what to avoid) and user validations (non-obvious approaches that worked) to avoid creeping timidity.
- **Epistemic Guardrail**: "Memory says X exists ≠ X exists now." Always verify paths and symbols against the live codebase before acting.
- **Isolated Reference Extraction**: When referencing large external projects (e.g. DeepSeek Harness) for copying or inspiration, never point the implementation AI to the full upstream repo. Surgically extract only the target subsystem/primitives into an isolated folder (e.g. `references/<subsystem>/`) with an explicit AI guide, and clean up the upstream clone immediately to prevent dependency sprawl or mindless boilerplate copying. Link [[user-profile]], [[reference-windows-acl-sandbox]].
- **Verify Host Preconditions Before Porting**: A mechanism that works in its upstream project can be silently unavailable here — privileges this session does not hold, elevation, OS build. Probe the single decisive operation on this machine with one throwaway script before building on it, and treat a partially-applied mechanism (e.g. a lowered token with no matching label) as a bug class, not bad luck. Link [[reference-windows-acl-sandbox]].
- **Two-Tier AI Role Boundary (Architect vs Runner)**: When the user delegates implementation to an external "runner AI", this primary agent acts strictly as reviewer/architect to conserve quota and protect architectural boundaries. NEVER autonomously touch or test-modify files in the codebase. Write direct, self-contained, copy-pasteable prompt specs with exact target files, CSS/DOM preservation rules, and verification criteria for the runner AI, then perform read-only review and automated test validation on returned diffs. Link [[user-profile]].
- **No Premature Completion on Partial Passes**: When a multi-stage roadmap promises an end-to-end simulation or integration phase (e.g. Block 3), never declare milestone complete simply because individual unit tests in earlier blocks passed. Maintain strict accountability to all promised phases until full end-to-end verification lands. Link [[user-profile]].
- **Segregate Objective System Events from Agent Chat**: System-level notifications (such as balance transfers or economic alerts) must be cleanly partitioned into dedicated system reminder blocks (e.g. `# SYSTEM REMINDERS`) in LLM contexts rather than dumped into conversational message streams. This prevents model confusion between agent dialog and world events. Link [[user-profile]].
- **Transparent Plain-Language Explanation on Discrepancies**: When a delegate runner AI reports an internal adaptation or minor discrepancy from the spec (e.g. rebuilding an unexported test runner locally), explain the root cause, adaptation, and absence of technical debt to the user immediately in plain language without technical jargon. Link [[user-profile]].
- **Freeze Per-Entity Config as a Snapshot, Never as a Reference**: When a per-agent (or per-entity) setting must survive later edits to the shared catalogue, copy the resolved values into that entity's own home at bind time instead of storing a catalogue id. Referencing by id lets an operator's later edit silently change a living agent's behaviour — here, silently swapping its brain, which this project treats as changing the mind. Prefer "the entity keeps what it was given" over "the entity follows the menu". Link [[project-model-config-decisions]].
- **Read the Whole Task Brief Before Touching Code, and Re-Derive Its Design Forks**: A brief may specify shapes that contradict the user's actual intent, and may also **over-promise test damage**. This session's brief demanded changing `conservatory.config.json`, which would have put live API keys in a git-tracked file, and predicted that one existing test assertion must change — that assertion in fact needed no change, because the new write lived in a layer the tests never import. Verify the blast radius yourself instead of reporting the brief's estimate back as fact; the real number may be better *or* worse, and either way it must be measured. Link [[project-model-config-decisions]].
- **Secrets Must Not Land in a Git-Tracked File**: In this repo `conservatory.config.json` is tracked while `.env` is gitignored. Any new file that will hold an API key must be gitignored too. Before writing any credential to disk, check `git check-ignore` on the exact target path, and verify with `git diff` that no key string entered a tracked file. **A tracked file can be polluted by a process you did not start**: the user's own already-running `npm start` rewrote the config with live keys while the agent was only editing files. Check for a live instance before declaring a config change safe, and tell the user to restart rather than assuming the code he is running is the code on disk. Link [[project-model-config-decisions]].
- **Split Hand-Off Briefs by Topic or Sequential Stage (Write Prompts in English)**: When producing hand-off prompts for external runner AIs, write the prompt text itself in **English** (while still talking to the user in plain Chinese outside the prompt block). Either split independent topics for parallel execution OR—when changes build on one another—deliver **staged prompts one at a time** ("分阶段写提示词，写一个粘回来检查再写下一个") so the architect can review, run tests, and adjust mid-course between stages. Link [[user-profile]].

**Why:**
Prevents context drift, eliminates hallucinated assumptions, maintains balanced confidence, respects user intent alignment, and keeps blast radius strictly controlled.

**How to apply:**
Review these guidelines before proposing modifications, when handling ambiguous requests, or when recalling historical decisions. Link relevant cards via `[[topic-slug]]`.
